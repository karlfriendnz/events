Events: Pink Zebra × Friendly Manager
Integration spec · Simple event

Putting events back into Friendly Manager, built in Pink Zebra

A simple event lives in Pink Zebra, but it can't exist alone: its venue, its people and its money all belong to Friendly Manager. This is the ownership split, the API surface each side has to expose, and the flows that stitch them together.

PZ owns FM owns shared / synced

The shape of it

Pink Zebra is the event brain — it holds the event record, the registration form, the visibility rules and the terms. Friendly Manager stays the system of record for the club — its people, its venues, its money. Everything PZ needs from the club it fetches by ID; everything the club needs to know about a registration, PZ pushes back.

The linchpin: one identity, two systems

Everything above depends on a single rule: a person exists once, in FM, and PZ only ever holds a pointer to them. Get this wrong and you end up with duplicate members, split registration history and fees raised against ghosts.

What PZ stores per registrant

fm_person_idThe only durable link. Resolved at registration time.
fm_org_idWhich club the event belongs to — scopes every API call.
answers (jsonb)Custom form answers only. Core fields are not kept here.
terms_accepted_at / versionProof of acceptance.
fm_fee_idThe fee/invoice FM raised for this registration.

Matching rule: email is the match key. Exact match → use the existing FM person. No match → FM creates the person from the core fields and returns the new id. Ambiguous (same email, different name) → FM decides, PZ never guesses.

What FM has to expose

PZ can be built against a small, boring REST surface. Auth: a per-club API key or service token issued by FM, scoped to fm_org_id.

GET/api/venuesVenue list for the club — id, name, address. Read-only for PZ.
GET/api/people?search=Person search for the invitee + admin pickers.
GET/api/groupsGroups/teams, so an event can invite a whole group.
GET/api/groups/:id/membersExpand a group into people at invite time.
POST/api/people/resolveThe important one. Send core profile fields → FM matches by email or creates the person → returns fm_person_id. Idempotent.
POST/api/feesRaise a fee/invoice against a person, with an idempotency key so a retried registration doesn't double-charge.
GET/api/fees/:idPayment status, for showing "paid / unpaid" on the PZ registration list.
Idempotency is not optional

Both people/resolve and fees will be retried — by network failures, by double-clicks, by a registration that half-succeeded. Every write from PZ to FM carries a key (registration_id works) and FM returns the existing record rather than creating a second one.

What PZ has to expose back

GET/api/events?org=So FM can list a club's events in its own UI without owning them.
GET/api/people/:fm_person_id/registrationsSo an FM member profile can show "events they're registered for".
POST/webhooks/fee-paidFM tells PZ a fee was paid → PZ flips the registration to confirmed.
POST/webhooks/person-mergedFM merged two members → PZ repoints its fm_person_id references. Skip this and merges silently orphan registrations.

Decide before you build

Does payment happen in FM (PZ hands off to FM's payment page and waits for the webhook) or in PZ (PZ takes the money and tells FM it's paid)? Fees living in FM points strongly at the first — but it means the registrant leaves the PZ form to pay, and a half-finished payment leaves an unpaid registration you have to chase or expire.

The core-profile boundary

The fields in the FM member screen are the ones PZ must collect but not keep. Everything else on the form is PZ's.

FM  Written back to the member record

  • First / last name
  • Email, primary phone, alternate phone, work phone
  • Gender, date of birth
  • Address (street, suburb, city, post code)
  • Medical notes
  • Tags, school, referral type
  • Privacy (photo consent), newsletter opt-in
  • System access, join date — FM sets these, PZ never sends them

PZ  Stays with the event

  • Every custom question on the registration form
  • Which sessions / options they chose
  • Terms acceptance (timestamp + version)
  • Registration status and history
  • Anything event-specific: dietary for this event, t-shirt size, notes to the organiser

The rule to hold the line with: if a club would still want the answer after the event is over and forgotten, it's a core field and belongs in FM. If it only makes sense in the context of this event, it stays in PZ.

Open questions to settle first

  • Where does payment happen — FM's payment page, or PZ takes the money? This changes the registration flow, not just a setting.
  • Does FM show events at all, or does the events tab just deep-link into PZ? Deep-link is far cheaper and can be replaced later.
  • Recurring events and fees — one fee per series, or one per occurrence? FM's ledger needs to know.
  • What happens to an unpaid registration? Held, expired after N days, or confirmed anyway.
  • Member merges and deletions in FM — the webhook above is the answer, but someone has to own it.
  • Non-members registering publicly — do they become FM members the moment they register, or does FM hold them as contacts until someone approves?
